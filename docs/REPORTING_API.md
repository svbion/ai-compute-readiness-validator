# Reporting API and schema foundation

This document defines the GPUValidator reporting backend foundation. It covers persisted report metadata and the CRUD API used by the portal. Rich rendering and PDF/DOCX export are intentionally deferred.

## Schema

Report records are stored in the engagement store under `reports[]` with `schema_version: "1.0.0"`.

Required persisted fields:

| Field | Type | Notes |
| --- | --- | --- |
| `report_id` | string | Server-generated `rpt_<uuid>` identifier. |
| `name` | string | Human-readable report name. Required on create. |
| `report_type` | enum | One of the report types below. Required on create. |
| `status` | enum | Defaults to `draft` on create. |
| `scope_type` | enum | Report scope selector. Required on create. |
| `scope_id` | string/null | Identifier within the selected scope. |
| `customer` | string/null | Customer display name or account reference. |
| `engagement_id` | string/null | Source engagement identifier. |
| `cluster_id` | string/null | Source cluster identifier. |
| `agent_ids` | string[] | Source validation agent IDs. |
| `node_ids` | string[] | Source node IDs or hostnames when node IDs are not yet modeled. |
| `gpu_ids` | string[] | Source GPU IDs/UUIDs. |
| `validation_ids` | string[] | Source validation run IDs. |
| `benchmark_ids` | string[] | Source benchmark run IDs. |
| `evidence_ids` | string[] | Source evidence or validation result IDs. |
| `author_name` | string | Defaults to `Sabion P Frazier`. |
| `purpose` | string | Defaults to `GPUValidator interview demonstration`. |
| `confidentiality` | string | Defaults to `Confidential`. |
| `version` | integer | Starts at `1`. |
| `created_at` | ISO timestamp | Server-generated. |
| `updated_at` | ISO timestamp | Server-maintained on updates. |
| `generated_at` | ISO timestamp/null | Null for drafts; set when a renderer marks a report generated. |
| `checksum` | string | SHA-256 metadata checksum unless explicitly patched by a renderer. |
| `error` | string/null | Failure details when status is `failed`. |

## Source lineage behavior

On `POST /api/v1/reports`, callers may pass lineage arrays directly. The backend also derives lineage from persisted validation agents, validation runs/results, benchmark runs, evidence records, and GPU inventory for the requested `scope_type`/`scope_id`. Derived and explicit arrays are de-duplicated and persisted on the report record so every report keeps references back to validations, benchmarks, agents, nodes, GPUs, and evidence.

## API contract

All endpoints return `Cache-Control: no-store`.

### GET /api/v1/reports

Returns reports sorted by `updated_at` descending.

Response:

```json
{
  "reports": [
    {
      "report_id": "rpt_...",
      "name": "RunPod A100 Customer Validation Report",
      "report_type": "customer-validation",
      "status": "draft"
    }
  ]
}
```

### POST /api/v1/reports

Creates a report metadata record. Required request fields are `name`, `report_type`, and `scope_type`.

Example:

```json
{
  "name": "RunPod A100 Customer Validation Report",
  "report_type": "customer-validation",
  "scope_type": "validation_run",
  "scope_id": "val_123",
  "customer": "NVIDIA interview demo",
  "engagement_id": "eng_demo",
  "cluster_id": "cluster_runpod_a100"
}
```

Success: `201 Created` with `{ "report": { ... } }`.

### GET /api/v1/reports/:reportId

Returns one report record by `report_id`.

Success: `200 OK` with `{ "report": { ... } }`.

Missing report:

```json
{
  "error": {
    "code": "report_not_found",
    "message": "Report not found.",
    "details": []
  }
}
```

### PATCH /api/v1/reports/:reportId

Updates mutable report metadata. Server-owned fields `report_id` and `created_at` cannot be patched. `updated_at` is always server-maintained.

Common patch example:

```json
{
  "status": "approved",
  "version": 2,
  "confidentiality": "Customer Confidential"
}
```

A renderer can later mark a report generated by setting `status`, `generated_at`, and a renderer-produced `checksum`.

### DELETE /api/v1/reports/:reportId

Deletes a report metadata record.

Success: `204 No Content`.

## Validation errors

Invalid request bodies return `400 Bad Request` with a stable code and field-level details:

```json
{
  "error": {
    "code": "invalid_report_request",
    "message": "Report request validation failed.",
    "details": [
      { "field": "report_type", "message": "report_type must be one of: executive-summary, customer-validation, ..." }
    ]
  }
}
```

## Deferred work

The foundation does not implement PDF/DOCX export, rich template rendering, approval workflow enforcement, AI Copilot sections, NCCL/HPL/MLPerf expansion, or customer branding. Those should build on the persisted model and API contract above.
